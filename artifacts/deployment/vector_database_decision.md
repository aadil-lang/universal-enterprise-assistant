# Vector Database Architectural Decision Record (ADR)
## Evaluation of ChromaDB vs. Qdrant Cloud Free for Universal Enterprise Assistant

**Standard:** ESR-STD-v2.4  
**Date:** November 23, 2026  
**Document ID:** `ADR-VECTOR-STORE-001`  
**Status:** PROPOSED & EVALUATED  
**Authors:** Senior Engineering & Cloud Architecture Team  

---

## 1. Context & Problem Statement

The Acme Universal Enterprise HR & IT Assistant uses vector search to index, version, and retrieve corporate policies (e.g. Leave Policy, Remote Work Policy, Code of Conduct, IT Equipment Policy). 

In local development, the system relies on **ChromaDB 1.4.4** running as a Docker Compose service (`container_name: acme-chromadb`) with a named persistent volume (`chroma_data:/chroma/chroma`) and REST access via `chromadb.HttpClient(host="chromadb", port=8000)`.

The objective is to deploy the system to a free cloud hosting tier. We must evaluate whether ChromaDB can be retained in the cloud or if a migration to **Qdrant Cloud Free** is justified, without breaking local developer workflows or degrading retrieval accuracy.

---

## 2. Option A Evaluation: Preserve ChromaDB in Cloud Free Tier

### 2.1 Hosted ChromaDB Availability
* **Findings:** Chroma currently offers no public, permanent free-tier managed SaaS service (Chroma Cloud is currently in private waitlist/enterprise access).
* **Self-Hosting on Render Free:** 
  * Render Free provides ephemeral containers. Every time the web service idles (after 15 minutes of inactivity) or re-deploys, the container root filesystem is destroyed and re-initialized from the Docker image.
  * Render Persistent Disks are **not available** on the Free Tier; disks require a paid Starter plan ($7/mo per disk).
  * Hosting ChromaDB in an ephemeral container means all uploaded corporate policy vectors and SQLite index state are **wiped upon container spin-down**.
* **Self-Hosting on Alternative Free PaaS (e.g., Fly.io, Railway Free):**
  * Railway no longer offers a permanent free tier (trial credits expire).
  * Fly.io free allowances require credit card verification and provide limited shared CPU and ephemeral volume guarantees.

### 2.2 Feasibility Conclusion for Option A
> [!WARNING]
> Hosting ChromaDB on Render Free with local storage violates **Persistence Criteria (Section 12)**: any policy uploaded by HR Admin Alice would be completely lost after 15 minutes of inactivity. Retaining ChromaDB in the cloud is only viable if paying for persistent volumes, which contradicts the explicit **Free-Tier Constraint**.

---

## 3. Option B Evaluation: Migrate / Extend to Qdrant Cloud Free

### 3.1 Qdrant Cloud Free Capabilities
* **Free Tier Allocation:** 1 permanent cluster, 1 GB RAM, 0.5 vCPU, 4 GB persistent cloud storage.
* **Network & Security:** Managed HTTPS endpoint with API key authentication (`qdrant-client` over gRPC or REST on port 6333).
* **Uptime & SLA:** High-availability cluster, persistent SSD storage, zero automatic teardown on idle.
* **Vector Specifications:** 
  * Dimension: 384 dimensions (matches `sentence-transformers/all-MiniLM-L6-v2` and `ONNXMiniLM_L6_V2`).
  * Distance Metric: Cosine similarity (`Distance.COSINE`).
  * Payload Filtering: Native JSON metadata payload indexing for exact filtering (`document_id`, `document_checksum`, `section`, `category`, `page_number`).

### 3.2 Compatibility Matrix: ChromaDB vs. Qdrant

| Feature | Local ChromaDB | Qdrant Cloud Free | Equivalence & Parity Assessment |
|---|---|---|---|
| **Embedding Dimension** | 384 (all-MiniLM-L6-v2) | 384 (all-MiniLM-L6-v2) | **Identical** — Embeddings are generated by the app's `EmbeddingService` before storage. |
| **Distance Metric** | Cosine (`hnsw:space: cosine`) | Cosine (`Distance.COSINE`) | **Identical** — Mathematical dot-product / cosine distance. |
| **Document Identification** | `chunk_id` string (e.g. `{doc_id}_{checksum}_{idx}`) | String/UUID Point ID | **Supported** — Qdrant accepts UUID or unsigned integer point IDs, and stores custom string `chunk_id` in payload. |
| **Metadata Payloads** | Key-value dictionary | JSON payload dictionary | **Identical** — Stores `document_id`, `document_checksum`, `section`, `page_number`, `content_hash`. |
| **Versioning & Staging** | Two-phase staging with disjoint IDs | Two-phase staging with disjoint IDs | **Preserved** — Replacement chunks are verified before old version chunks are deleted. |
| **Filtering (Active Version)** | `where={"document_checksum": active_hash}` | `Filter(must=[FieldCondition(key="document_checksum", match=MatchValue(value=active_hash))])` | **Preserved** — Exact metadata filtering supported. |

## 4. Architectural Decision: The Unified Vector Store Provider Pattern

To avoid breaking local development and satisfy cloud persistence requirements without cost, we implement the **Provider Factory Pattern** inside `apps/api/app/services/vector_store.py`:

```
                                  +----------------------------+
                                  |     VectorStoreService     |
                                  |  (Abstract Base Interface) |
                                  +--------------+-------------+
                                                 |
                        +------------------------+------------------------+
                        |                                                 |
                        v                                                 v
         +------------------------------+                  +------------------------------+
         |     ChromaVectorStore        |                  |      QdrantVectorStore       |
         |  - Local Docker Compose      |                  |  - Cloud Production          |
         |  - Ephemeral test runs       |                  |  - Neon + Render Free Stack  |
         |  - Port 8000 HTTP            |                  |  - Persistent 4GB Cluster    |
         +------------------------------+                  +------------------------------+
```

### Configuration Switch (`VECTOR_STORE_PROVIDER`):
* `VECTOR_STORE_PROVIDER="chroma"` (Default for local development and unit tests):
  Uses existing `chromadb.HttpClient` or `chromadb.EphemeralClient`.
* `VECTOR_STORE_PROVIDER="qdrant"` (Production cloud deployment):
  Uses `qdrant-client` connecting to `QDRANT_URL` and `QDRANT_API_KEY`.

## 5. Retrieval Quality Verification Plan

To verify that Qdrant produces identical grounding quality to ChromaDB before accepting the migration, the following representative test queries are evaluated:

| Query ID | Representative Question | Expected Policy Document | Expected Section | Grounding Target |
|---|---|---|---|---|
| **Q1** | *"What is the annual leave accrual and rollover limit?"* | `Acme_Leave_Policy.pdf` | Annual Vacation Leave | 18 days accrual, 5 days max rollover |
| **Q2** | *"How many days of sick leave can I carry over?"* | `Acme_Leave_Policy.pdf` | Sick Leave Accrual | 10 days sick leave, 5 days rollover cap |
| **Q3** | *"Can I work remotely from outside the country?"* | `Acme_Remote_Work_Policy.md` | Geographic Restrictions | Remote work must be within country of employment |
| **Q4** | *"What is the standard equipment refresh cycle?"* | `Acme_IT_Equipment_Policy.pdf` | Hardware Lifecycle | Standard laptop refresh is every 36 months |

### Acceptance Criteria:
1. Top-1 retrieved chunk in Qdrant must match the authoritative section and policy document retrieved by ChromaDB.
2. Cosine similarity score margin must be within $\pm 0.02$ tolerance.
3. Strict active-version filtering must correctly isolate updated policy versions and ignore obsolete checksums.

---

## 6. Final Decision & Sign-off

* **Decision:** **Adopt Dual-Provider Architecture (Option B for Cloud, Option A for Local).**
* **Rationale:** Preserves 100% of local developer ergonomics, Docker Compose functionality, and automated unit test speed (via in-memory ChromaDB), while providing enterprise-grade persistent vector storage on Qdrant Cloud Free at zero cost.
